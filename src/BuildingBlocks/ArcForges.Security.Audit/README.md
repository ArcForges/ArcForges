# Local security audit (PLT.44)

`ArcForges.Security.Audit` owns an owner-scoped SQLite file whose security-event table is `local_audit`. It is separate from PLT.01 product content/journal storage and has no dependency on `ArcForges.Observability`; neither system queries or projects the other's records. The library reuses the already-admitted `Microsoft.Data.Sqlite` 10.0.12 closure and is deliberately non-packable here: the repository policy test requires every packable project to be listed in `eng/packaging/packages.json`, and PLT.44 does not select a package identity, edit the package inventory, or publish the package. PLT.46 owns package admission (including enabling packing for this project) and pack, publish, and consumer acceptance.

Callers select an explicit database path, realm/account owner, and finite `AuditRetentionPolicy`. The file binds its owner, retention duration, and policy ID on first creation and fails closed if a later open disagrees. Retention is divided into complete UTC calendar months. A month becomes eligible only after its last instant plus the configured retention days; there is no implicit infinite-retention default.

An `AuditEvent` has a closed event/risk/decision/reason/origin vocabulary, the complete PLT.36 `ActorChain`, executor and software identity, a canonical capability key, an opaque typed resource ID, and optional workspace/task/correlation IDs. The shape deliberately has no message, payload, arbitrary tags, paths, secret values, prompts, or document content. A caller must authorize append and query operations at its composition boundary; owner-scoped storage is not a substitute for an application access-control decision.

All appends and maintenance run through one in-process path lock and SQLite's serialized write transaction. SQLite triggers and a connection authorizer reject ordinary updates/deletes; the maintenance gate is connection-private and transaction-scoped. Purge and hold-release entry points are internal to the assembly. The dedicated policy-retention authority privately mints a nonserializable capability bound by object-reference identity to one store, policy, owner/month/action, hold (for release), and a five-minute window. Ordinary callers cannot construct, deserialize, or request this capability, and string role names are not accepted. An active hold blocks purge. Event deletion, the consumed authority-actor/software receipt, and the immutable purge receipt commit together. Receipts are durable audit evidence, not cryptographically signed approvals. The purge receipt retains the exact partition, row count, sequence coverage, SHA-256 over ordered event identities/digests, and full authority actor chain.

## Typed intakes (egress decisions and capability-lease lifecycle)

The generic `AuditStore.Append` path cannot express these facts incorrectly: `AuditEvent` enforces closed per-type shapes, so a `DataEgressAuthorized`/`DataEgressDenied` event requires typed `AuditEgressDetail` (data class, destination class, canonical destination identity, authority ID with committed revision), a correlation, and an allowed/denied decision with an agreeing reason; a capability-lease event requires the `CapabilityLease` resource kind and the decision/reason of its lifecycle kind; no other event type may carry either. `AuditRisk` mirrors the R0-R4 scale without loss. Neither shape has content, secret, path or property-bag fields.

`EgressDecisionAuditAdapter.Record(EgressDecisionFact)` appends one allowed or denied egress decision synchronously and returns only after the row is committed. `CapabilityLeaseAuditAdapter.Record(CapabilityLeaseLifecycleFact)` appends one issued, revoked, expired or task-ended fact and stores `AuditCapabilityLeaseId.Value` directly as the Guid-valued resource identity (never stringified, hashed or truncated). Both let every failure propagate, so an enforcement path that calls `Record` before releasing a transfer cannot release an allowed transfer whose audit append failed. Facts are validated at construction; unknown lifecycle kinds, empty identities and contradictory decision/reason pairs are refused.

`ArcForges.Security` owns the egress and lease sink ports and never references this project. **Lease lifecycle (integrated).** `CapabilityLeaseEventAuditSink` implements the PLT.43 `ILeaseEventSink` over `CapabilityLeaseAuditAdapter`, so the real `CapabilityLeaseManager` writes its issued, revoked, expired and task-ended facts to the audit store. The mapping is closed: `CapabilityLeaseId.Value` is the audit resource Guid, the event kind maps one to one, the reason comes from the lease's own issue basis or revocation reason (policy-allowed, user-approved, step-up, risk-accepted; owner-revoked becomes user-rejected, authority-lost becomes authority-missing; expiry is policy-expired; task end is not-applicable), and risk, task, workspace and origin come from the lease. The actor chain is the delegator's issuing chain (the lease snapshot does not record the revoking principal), the software identity is the issuing chain's final actor or the composition root's fallback for a direct issue, and the occurrence time is stamped by the store at append (an expiry fact written by a later sweep is stamped at the sweep, not at the expiry instant). A fact the audit shape cannot hold (a capability key that is not a canonical audit key, another owner's lease, a purged partition, a disposed store) throws, so the manager refuses the issue (`AuditUnavailable`) or reports the end fact as still owed and retries it on the next sweep. Facts are written at least once. The offline tests drive the real `CapabilityLeaseManager` against a real `AuditStore` with an in-memory lease store; they do not run any host composition root or a durable lease store.

**Egress decisions (not integrated).** `EgressDecisionFact` is still an audit-owned closed intake with no compile-time link to the delivered PLT.41 `EgressAuditRecord`, and no sink maps one to the other, because the delivered record cannot fill the typed audit event without inventing data: it carries no effective risk, its resource is an opaque string identity and revision (the audit resource is a Guid), its authority is an `EgressAuthorityKind` plus a free-text reference (the audit detail requires an object Guid and a committed revision), its data classes (public, diagnostic, workspace, sensitive, secret) are not the audit's classification, and decisions refused before classification have no destination class or data class (the audit detail requires them). Resolving that needs a contract decision across PLT.41 and this store; see the PLT.44 ledger record.

Legal holds are append-only place/release facts with full actor chain, software identity, origin, and a typed reason. A hold ID is never reused. Hold placement authorization remains the owning application's responsibility; release and purge are additionally fenced by the configured policy-retention authority.

This protects against ordinary API/SQL roles; it does **not** make a desktop-local file tamper-proof. A person who controls the machine or database file can replace or modify that file, so callers and product copy must not claim otherwise. The library does not silently export, sync, join, or correlate audit with telemetry.

## Known limits and availability consequences

- **No production retention runner yet.** `CreateMaintenanceCapability`, `PurgeExpiredPartition` and `ReleaseLegalHold` are internal on purpose (the capability is internally minted and never reachable by ordinary callers), and only the test project sees them. The mechanism and its offline tests are delivered; nothing a host composition root can call runs retention, so AU-11 is satisfied by the mechanism, not yet by an invocable runner. A narrow public runner (purge only expired, unheld partitions under the declared policy, no caller-chosen partition or time) is an open follow-up with no assigned owner in this task.
- **Clock rollback after a purge.** Once a month has a retained purge receipt, an append stamped inside that month (the wall clock moved back by more than the retention window) is refused with `InvalidOperationException`, so an enforcement path that records before releasing a transfer fails closed until the clock moves on. This is an intentional availability trade-off in favour of the safe direction.
- **One corrupt row poisons its page and month.** Raw `INSERT` into the event table is not blocked (append semantics) and a person controlling the file can drop triggers. A row that fails verification (digest, owner, policy, partition, executor or closed event shape) makes every `Query` page containing it, and every purge of its month, throw `InvalidDataException`; there is no quarantine. This is fail-closed and consistent with the file not being tamper-proof.
- **Schema version.** `SchemaVersion` stays 1 although the unmerged draft's file layout and the event digest domain (`event.v3`) changed; no draft file was ever published, and a file created from the unmerged draft will not open.
- **Egress mirror not integrated.** `EgressDecisionFact` is an audit-owned mirror of the delivered PLT.41 egress record with no mapping from `EgressAuditRecord` (see the typed intakes section for the exact missing facts). The lease side is integrated through `CapabilityLeaseEventAuditSink`; `AuditCapabilityLeaseId` carries the same Guid as `CapabilityLeaseId`.
- **Not covered.** No cross-process writer test (an in-process semaphore plus SQLite's write lock only), no Native AOT publish, no package pack of this project (it is non-packable here; PLT.46 owns admission).

Offline tests exercise event completeness and round-trip integrity, owner scoping, ordinary SQL mutation refusal, inability of ordinary callers to obtain capabilities, wrong-store/policy/owner/action and expired capability refusal, expired/unexpired partitions, legal-hold enforcement/release, typed egress and lease intake shape/identity/fail-closed behavior, durable non-signature authority and purge receipts, append serialization, and telemetry separation.
