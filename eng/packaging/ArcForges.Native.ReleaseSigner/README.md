# Native publisher signing adapter

This nonpackable offline tool signs or verifies the exact manifest/profile bytes and source/version/RID identity using the existing ES256 production contract. It never loads a native library, invents publisher enrollment or treats a self-declared public key as authority. The release pipeline independently verifies the complete source-bound producer stage before invocation and supplies its separately approved DER SubjectPublicKeyInfo file.

The release compositor executes a reviewed self-contained NativeAOT build from a genuinely OS-protected installation, holding the entire pinned payload for the operation. A user-owned build directory or mutable dotnet host/framework is refused by production composition. Managed SDK builds remain developer/component diagnostics. Provisioning protected tool ownership/DACLs and publisher keys is a separate real release prerequisite, not a side effect of this CLI or a test fixture.

Commands require `--manifest`, `--profile`, `--approved-spki`, `--key-id`, `--rid`, `--library`, `--version` and `--source`. `sign` also requires a new `--output` and exactly one actual provider: `--pem` (unencrypted PKCS8/EC PEM reference) or `--certificate-thumbprint` plus `--store-location CurrentUser|LocalMachine` (My store). Certificate selection requires one current code-signing leaf with an actual ECDSA private provider. The private provider must match the independently approved P256 public key; private material is never emitted. `verify` requires `--signature` and accepts no private provider or output arguments.

Reads and output are bounded. Cancellation refuses before promotion; create-only atomic publication preserves an existing candidate, including competing writers. Owned file bytes are flushed before rename. The surrounding release composition must persist the destination directory on POSIX and reverify the promoted envelope; this tool does not claim physical power-loss durability. Missing, foreign or inaccessible production credentials fail closed. Generated component test keys are not production enrollment, Authenticode signing, native execution or deployed acceptance.

The Windows helper adapter uses the reviewed Microsoft SDK 10.0.28000.0 x64 `signtool.exe` at its protected installed location and holds its exact SHA256-pinned executable open throughout invocation. `verify-helper` requires `--tool`, `--input` and the independently approved `--certificate-thumbprint`; it invokes actual Authenticode `/pa /all /tw` policy and verifies the embedded primary signer plus RFC3161 timestamp and refuses unsigned or untrusted executable bytes. `sign-helper` requires `--tool`, `--input`, `--input-sha256`, `--output`, `--certificate-thumbprint`, `--store-location` and an HTTPS `--timestamp` RFC3161 endpoint. It selects a current private code-signing leaf from the specified My store, copies only the approved bounded unsigned bytes, signs with SHA256, then requires actual trust verification, the selected leaf certificate SHA256, and actual RFC3161 evidence before create-only promotion. One two-minute operation budget covers copying, signing and verification. Diagnostics are drained under a strict bound and never exposed; cancellation or tool failure terminates the actual process tree and requires exit before temporary cleanup. This is a production adapter, not evidence of an enrolled ArcForges code-signing certificate or successful signed publication.
